用 Python + FFmpeg 写一个延时摄影合成脚本#

环境：Windows 10 / FFmpeg 9.0.1 (gyan.dev full build) / Python 3.12

硬件：i7-10710U（6 核 12 线程）/ 16 GB / MX350 + Intel UHD

素材：尼康 D810，7360×4912 JPG（3600 万像素）

一、需求#

1.1 场景#

拍延时摄影的人都会遇到同一个问题：拍的时候很爽，合的时候很烦。

一次日出就是 700 多张 7360×4912 的 JPG，累计几个小时。拍完只是第一步，真正折磨人的是后期——总不能每次都在 Premiere 里拖几百张图，或者手敲 ffmpeg 命令。

1.2 需求清单#

把脑子里模糊的想法整理成可以验收的条目：

编号需求验收标准
R1一条命令批量合成给个文件夹就能出片，不用手工列文件
R2输出要到处都能播手机、电视、Windows 自带播放器、PC 播放器都能放
R34K 导出速度可接受700 张不能等到天荒地老
R4文件名可辨识隔几天翻回去还能认出是哪次拍摄
R5运行时有反馈知道跑到哪了、还要多久，而不是干等
R6参数可调帧率、分辨率、画质、速度能按需开关

其中 R2 是硬需求。视频做出来自己看是一回事，发给别人、拷到电视上放是另一回事——如果对方打不开，这个片子等于没做。

R5 看起来是”锦上添花”，但 700 张的渲染动辄几分钟，没有进度反馈的等待体验极差，实际上是刚需。

二、思路#

2.1 为什么不直接用剪辑软件#

Premiere / DaVinci 都能做图片序列，但：

  • 几百张 3600 万像素图导入时间轴，内存和显存压力巨大；
  • 参数调整靠鼠标点，批次处理不现实；
  • 最关键的——它们不解决”输出能不能播”的问题，导出参数照样得自己懂。

所以正确的分工是：Python 负责编排（找图、拼清单、调参数、并行、报进度），FFmpeg 负责真正的解码与编码。FFmpeg 才是这件事的核心工具，脚本只是把它包成一个顺手的命令行工具。

2.2 为什么用 concat demuxer#

FFmpeg 合成图片序列有两条路：

方案 A：图片序列模式

要求文件名必须从 ​1​ 开始、连续编号、固定位数。而相机的实际文件名是 ​810_2161.JPG​ 这种，中间还可能缺号，不满足条件。

方案 B：concat demuxer

list.txt 里逐个列出文件，还能给每张图单独指定显示时长：

对文件名没有任何要求，任意命名、任意顺序都能用。所以选 B。

2.3 整体架构#

关键决策有两个：

  1. 默认不按原图分辨率输出。 R2 的成败直接由分辨率决定，所以默认收到一个兼容性安全的值，想要大尺寸显式指定。
  2. 速度靠多进程而不是多线程。 原因见原理 3.5，这个结论是实测出来的，和直觉相反。

2.4 技术选型#

环节选择理由
语言Python 3编排逻辑清晰，标准库够用
合成FFmpeg + concat demuxer见 2.2
编码器libx264兼容性最好；硬件编码实测无价值（见 5.6）
尺寸探测ffprobe随 FFmpeg 一起装，无需额外依赖
进度-progress pipe:1FFmpeg 官方的机器可读进度
并行subprocess + 线程读管道单进程解码是瓶颈，只能靠多进程（见 3.5）

三、原理#

要满足 R2 和 R3，必须先搞清楚四件事：这个视频格式为什么会在某些设备上打不开、为什么网络播放会失败、为什么颜色会不对、以及时间到底花在哪。

3.1 concat demuxer 是怎么把图片变成视频的#

图片本身是”静止帧”，没有时间概念。concat demuxer 通过 ​duration​ 指令给每张图赋予持续时长，FFmpeg 再按这个时长推进 PTS（显示时间戳），于是静止帧就变成了时间轴上连续的画面。

所以帧率并不是直接写进编码器的，而是通过 duration 间接决定的。这也解释了为什么不能同时用 ​-framerate——那会和 duration 打架。

3.2 H.264 Level 与宏块上限 —— 决定”能不能播”#

这是全文最重要的原理，直接决定 R2。

H.264 不是”分辨率越高 Level 越高”这么简单，它按宏块（Macroblock） 算。一个宏块 16×16 像素，一帧的宏块数是：

每个 Level 规定了 MaxFS（最大帧尺寸，单位宏块） ：

LevelMaxFS（宏块）换算像素上限
5.022,0805,652,480
5.136,8649,437,184
6.0 / 6.1 / 6.2139,26435,651,584

拿实际数字算一遍就明白了：

为什么这决定”能不能播”？ 因为设备的 H.264 硬解能力普遍只做到 Level 5.1（约 4K）。超过这个 Level，解码器会直接拒绝——不是”放得卡”，是根本不解码。

而 PC 上的 VLC / PotPlayer 走软件解码，任何 Level 都能处理。

这就埋下了整个项目最大的坑：同一批文件，PC 上正常，手机上打不开。播放环境不同，结论不同，极容易被误判成”文件随机损坏”。

3.3 moov 原子与 faststart —— 决定”能不能边下边播”#

MP4 是”盒子结构”（box / atom）。其中两个最关键：

  • ​mdat​：真正的音视频数据
  • ​moov​：元数据（时长、轨道、编码参数、每一帧的位置索引）

FFmpeg 默认边编码边写 ​​mdat​​ ，最后才回填 ​​moov​​。于是 ​moov 落在文件末尾。

后果有两个：

  1. 流式播放失败。 播放器必须拿到 ​moov 才知道怎么解码。放在末尾意味着必须把整个文件读完才能开始——网络盘、U 盘、手机上”边下边播”就会表现为打不开。
  2. 中断即报废。 如果渲染中途被 Ctrl+C，​moov​ 根本没机会写入，得到一个结构不完整的 mp4，彻底不可播。

-movflags +faststart​ 让 FFmpeg 编码完后再做一次”搬移”，把 ​moov 挪到文件开头。

3.4 color range —— 决定”颜色对不对”#

数字视频的 YUV 取值有两种约定：

  • limited range（tv） ：Y 取值 16~235，标准的广播/视频范围
  • full range（pc） ：Y 取值 0~255，JPEG 家族用的范围

JPEG 是 full range，所以相机产出的 JPG 是 ​yuvj422p​（​j 就是 full range 的标记）。

坑在于：​ ​-pix_fmt yuv420p​​ 只转换”像素格式”，不会改变 range 标记。

也就是说，写了 ​-pix_fmt yuv420p​，输出仍然是 full range——在容器里被标成 ​yuvj420p。部分播放器拿到这种标记会渲染错误（偏色、发灰，个别硬解花屏）。

其中：

  • libx264 编码：默认就自动多线程，线程数约为 1.5× 物理核心数。
  • swscale 缩放：单滤镜内基本是串行的。
  • JPEG 解码：这是关键。FFmpeg 的 MJPEG 解码器实测是单线程的——​utime ≈ rtime​ 说明它只占用约 1 个核，​-threads 对它完全无效。

结论：图片序列的瓶颈是单线程的解码器，而不是编码器。 所以”让 ffmpeg 多线程”这条路走不通，唯一的出路是把图片列表切片，同时跑多个 ffmpeg 进程，把各自解码好的分片再用 ​-c copy 无损拼接起来。

-c copy​ 是流拷贝，不解码不重编码，所以拼接几乎不花时间。

4.5 进度条#

FFmpeg 默认往 stderr 刷日志，既刷屏又程序化解析困难。正确做法是用官方的机器可读进度：

-progress pipe:1​ 会每 0.5 秒往 stdout 打一行 ​key=value​，我们只关心 ​frame=N。

多进程时，为每个 ffmpeg 起一个读线程，各自维护自己的 ​frame，加锁汇总。百分比和 ETA：

渲染时把 stderr 重定向到临时文件，只在失败时才打印，成功路径下一条日志都看不到。

4.6 自动命名#

延时摄影没有官方命名标准，但视频/影视交付领域有个通行做法：ISO 日期打头 + 统一分隔符，好处是文件名按字典序排 = 按时间排，且跨语言无歧义（不会纠结 ​09-10 是 9 月 10 日还是 10 月 9 日）。

  • 分辨率写真实像素而不是 “4K”。因为 ​-4k 模式输出的是 3200 宽（原理 3.2 的妥协），标成 4K 就是错的。写实际尺寸最诚实，这也是 4.2 里坚持自己算尺寸的原因。
  • 日期从文件夹名解析（我的文件夹都是 ​20260924-描述 这种），解析不到就用第一张图的修改时间兜底。

五、排错#

5.1 症状：“有些视频能播，有些播不了”#

这是启动整个优化过程的原始问题。把已生成的视频全部 ​ffprobe 一遍：

文件分辨率Level结果
全尺寸输出7360×49126.2手机/电视打不开
手动缩过的那个1920×12825.0到处都能播

规律立刻显现：能播的都是低分辨率。对照原理 3.2，元凶是 Level 超限——而且”PC 能播、手机不能播”正是软解 vs 硬解的差异，完美解释了”随机性”的假象。

5.3 定位 color range 问题#

-pix_fmt​ 明明写了 ​yuv420p​，输出却是 ​yuvj420p​。对照原理 3.4 才知道 ​-pix_fmt​ 管不了 range。改用 ​scale=...:out_range=tv​ 之后，​ffprobe​ 确认变为 ​yuv420p / color_range=tv。

5.4 速度排查：多线程为什么没用#

R3 的第一反应是”让 ffmpeg 多线程”，实测结果反直觉。

12 张 7360×4912 → 4K，25fps：

配置耗时
-preset medium（原默认）4.67s
-preset veryfast3.66s
-preset ultrafast3.36s
medium​ + ​-threads 124.72s

​-threads 12​​ 和默认毫无差别。 于是把流程拆开，用 ​-benchmark 单独测每个阶段：

阶段耗时utime / rtime
只解码2.72s2.703 / 2.724
解码 + 缩放 4K2.89s—
解码 + 缩放 1080p2.88s—
完整 4K 输出（medium）4.67s—

结论清晰：

  1. 解码独占 2.72s，缩放+编码总共只有 0.17s；
  2. utime ≈ rtime​ 证明 MJPEG 解码是单线程；再试 ​-threads 6​：​utime=2.688 / rtime=2.725，纹丝不动。

还有个附带发现：4K（2.99s）和 1080p（2.92s）几乎一样快——因为大头是解码 3600 万像素的源图，跟输出多大无关。

既然单进程卡死，就上多进程（实现 4.4）。实测：

  • 6 进程 × 2 张，纯解码：2.72s → 0.894s
  • 6 进程 × 2 张，完整编码：2.99s → 1.14s
  • 端到端 24 张 4K：​ ​-j 1​​ 6.82s → ​ ​-j 6​​ 3.35s，约 2 倍

5.6 走不通的路：NVENC / QSV / GPU 解码#

方案结果
h264_nvenc（MX350）❌ ​Cannot load cuMemAllocAsync，老驱动 + 该卡 NVENC 支持残缺
hevc_qsv❌ ​Error querying encoder params: unsupported
h264_qsv✅ 可用，3.83s —— 但对照 5.4，编码阶段总共才 0.17s，加速编码解决不了瓶颈

结论：这台机器上硬件加速没有价值。 瓶颈在 CPU 解码，不在编码，老老实实用 libx264。当然换成有正经独显的台式机，结论可能完全不同——所以这些是”实测”而非”定论”。

5.7 4K 的等级陷阱#

做完上面所有优化，我想加个”一键 4K”，结果又踩了一次原理 3.2 的坑。

因为照片是 3:2，宽度 3840 对应高度 2562：

“标准 4K 宽度”3840 在 3:2 比例下刚好顶破 Level 5.1，被判成 6.0，兼容性问题原地复活。实测各宽度：

最终取舍：​-4k​ 模式用 3200 宽，稳在 Level 5.1（3200×2136 观感已经接近 4K），再叠上 ​ultrafast​ 和自动并行。真想要 4K 就 ​-4k -s 3840，自行接受 Level 6.0。

注意：16:9 素材的 3840×2160 是 Level 5.1，没这个问题。只有 3:2 / 4:3 这类”高”比例才会撞上限。
